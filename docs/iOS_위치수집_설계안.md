# iOS 위치 수집 설계안 — "연속 추적 → 5회 샘플" 방식

> 안드로이드는 무음 푸시로 정해진 시각에 위치를 1회씩 수집한다. iOS는 서버가 정한 시각에
> 백그라운드 앱을 깨우는 것을 허용하지 않으므로, 다른 방식이 필요하다. 이 문서는 그 대안 설계안이다.

---

## 1. 핵심 아이디어

- 근무 세션(출근~퇴근) 동안 **위치 매니저를 계속 켜 둔다.** 이 "연속 추적"의 목적은 좌표를 자주 저장하는 게 아니라 **앱을 백그라운드에서 살아있게 유지**하는 것.
- 앱이 살아있으면 **내부 타이머가 동작** → 미리 받아둔 **랜덤 5시각**에만 현재 위치를 읽어 서버(`/api/random-check/native-submit`)로 전송.
- 결과: 서버로 전송되는 건 **하루 5회**. 근무지 반경(500m) 판정만 필요하므로 **저정밀(100m급)** 로 운용해 배터리를 아낀다.

## 2. 추적 간격·정확도 권장값

| 항목 | 권장값 | 이유 |
|------|--------|------|
| desiredAccuracy | `kCLLocationAccuracyHundredMeters` (~100m) | 반경 500m 판정에 충분, 배터리 절약 |
| distanceFilter | 100m | 100m 이상 움직일 때만 업데이트 → 정지 시 콜백 최소화 |
| pausesLocationUpdatesAutomatically | `false` | iOS가 임의로 추적을 멈추지 않게 |
| allowsBackgroundLocationUpdates | `true` | 백그라운드 유지 |
| showsBackgroundLocationIndicator | `true` | 상단 위치 표시(투명성·심사 요건) |

- **실제 서버 전송은 밑단 스트림 간격과 무관하게 "5개 시각"에만** 일어난다.
- 정지 상태에서 스트림이 뜸해도, 앱은 살아있어 타이머가 마지막 알려진 위치(lastKnownLocation)를 전송할 수 있다.

## 3. 생명주기 (배터리 관리)

- **출근 버튼** → 위치 매니저 시작 + 그날 랜덤 5시각 스케줄 로드.
- **퇴근 버튼** → 위치 매니저 중지.
- **퇴근 누락** → 기본 퇴근시간 **+2시간**에 자동 중지. (안드로이드와 동일 규칙)
- 근무 시간 외에는 추적하지 않음. → "종일 추적"이 아니라 **근무 세션 한정**.

## 4. 권한·Info.plist 문구

"항상 허용" 권한이 필요하다. 처음 로그인 동의 화면에서 목적을 안내하고, 시스템 권한 요청 시 아래 문구를 노출한다.

```
NSLocationWhenInUseUsageDescription
  = "출퇴근 기록과 근무 중 위치 확인을 위해 위치를 사용합니다."
NSLocationAlwaysAndWhenInUseUsageDescription
  = "근무 시간 동안 하루 최대 5회 무작위로 위치를 확인해 실제 근무 여부를 점검합니다.
     이를 위해 '항상 허용'이 필요하며, 근무 시간 외에는 위치를 수집하지 않습니다."
UIBackgroundModes = ["location"]
```

- iOS는 "항상 허용"을 바로 안 주고 "앱 사용 중"부터 주는 경우가 많다. 앱은 이후 상승 요청을 통해 "항상 허용"으로 올리도록 안내한다.
- iOS가 주기적으로 "이 앱이 위치를 사용 중" 알림을 띄우며, 사용자가 언제든 "앱 사용 중에만"으로 낮출 수 있다(그 경우 백그라운드 수집 불가 → 로그인 동의문에 명시).

## 5. 배터리 고려

- 저정밀(100m) + distanceFilter 100m로 **정지 시 콜백을 최소화**.
- **근무 세션 한정** 실행(출근~퇴근/+2h)으로 하루 대부분 추적 정지.
- 필요 시 5시각 **직전 몇 분만 고정밀로 상향**하고 평소엔 저정밀로 두는 최적화도 가능(구현 복잡도↑).

## 6. 앱스토어 심사 고려

- **명확한 목적 고지**: 근태 확인용, 근무 시간 한정, 하루 최대 5회. 위 UsageDescription에 구체적으로 기재.
- **개인정보 처리방침**(위치 수집·보관·목적·기간)과 앱 **개인정보 라벨(nutrition label)** 에 위치 사용을 정확히 표기.
- **사용자 동의**: 최초 로그인 시 동의 절차(이미 존재). 회사 배포용이어도 App Store 심사 시 백그라운드 위치는 사유가 분명해야 반려되지 않는다.
- 백그라운드 위치 인디케이터(`showsBackgroundLocationIndicator=true`)로 투명성 확보.
- ⚠️ 무음 푸시로 몰래 추적하는 형태는 지양(심사 위험). "연속 추적 + 표시"가 오히려 심사에 안전하다.

## 7. 구현 메모 (Capacitor)

- 현재 안드로이드는 `TimeCardMessagingService`(FCM) 경로. iOS는 이 경로가 성립하지 않는다.
- iOS 백그라운드 위치는 `@capacitor/geolocation`만으로는 부족하다. **네이티브 `CLLocationManager` 구현**(Capacitor 플러그인) 또는 `@capacitor-community/background-geolocation` 같은 백그라운드 위치 플러그인이 필요하다.
- 서버 제출 엔드포인트는 기존 `/api/random-check/native-submit`(단기 JWT)를 재사용 가능.
- 랜덤 5시각은 안드로이드와 동일하게 서버가 생성(주말·공휴일·비정기 제외 규칙 그대로).

## 8. 한계 (솔직히)

- 사용자가 "항상 허용"을 "앱 사용 중"으로 낮추거나, iOS가 배터리 사정으로 백그라운드를 회수하면 수집이 끊길 수 있다.
- "종일이 아니라 5번만"이 목표지만, 그 5번을 백그라운드에서 잡으려면 **근무 시간 동안 위치 매니저를 켜 둬야** 하므로 내부적으로는 "근무 세션 연속 추적"이 된다.
- 앱을 켠 상태(포그라운드)에서는 이런 제약 없이 안정적으로 수집된다.

## 9. 대안 (더 단순하게 가려면)

- iOS는 **앱을 켠 상태에서만 수집**으로 두고, 백그라운드 자동 수집은 **안드로이드 전용**으로 유지.
- 또는 5시각에 **로컬 알림**을 보내 사용자가 탭하면 앱이 열려 위치를 수집(반자동). 배터리·심사 부담이 가장 적지만 사용자의 탭이 필요.
